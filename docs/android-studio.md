# Android Studio — the five things Carl actually does

Written because the Android Studio interface hides most of this behind menus that move
between versions. Everything here has a Terminal equivalent, and the Terminal is the
reliable one: it does the same thing on every version and it says what happened.

**Opening the Terminal inside Android Studio:** the `Terminal` tab along the bottom edge of
the window, or `Alt+F12`. It opens already in the project folder, so the commands below can
be pasted as-is.

---

## 1. Get Claude's changes (pull)

```
git pull
```

That's it. If it prints `Already up to date.` then nothing new has been pushed yet.

If it refuses because of local changes, see [When git complains](#when-git-complains).

**GUI equivalent:** main menu → `Git` → `Pull…` → `Pull`.

---

## 2. Send your changes (commit and push)

**Commit alone does nothing Claude can see.** A commit is local to the laptop; only a push
reaches GitHub. This is the step most often missed.

```
git add carlsbrain/schemas/
git commit -m "Commit exported Room schemas"
git push
```

**GUI equivalent:** the `Commit` tab down the left-hand edge (or `Ctrl+K`).

- Tick **only** the files that belong in the commit.
- Type a message in the box.
- Use the **Commit and Push…** button, not plain **Commit**. Plain Commit leaves the work
  on the laptop.

### What never gets committed

If any of these appear in the Commit panel under **Unversioned Files**, leave them unticked:

| File | Why |
|---|---|
| `carlsbrain-release.apk` | Build output, rebuilt every time |
| `*.dm` under `baselineProfiles` | Build output |
| `output-metadata.json` | Build bookkeeping |
| anything under `build/` | Build output |

`.gitignore` should now be hiding all of these. If they still show up, say so — it means a
rule is missing.

### What always gets committed after a database change

`carlsbrain/schemas/*.json`. These are generated by the build, and `MigrationTest` reads
them to verify migrations. Since August 2026 **a missing schema fails the test** rather than
skipping it, so a red `exportedSchemas_areCommitted` means exactly one thing: build once, then
commit whatever new `schemas/NN.json` appeared.

Right now **27.json and 28.json are missing** (24.json was lost and cannot be recovered without
temporarily reverting the database version, which is not worth doing — that migration has been
running in production for weeks). After your next successful build they will appear; commit them
and the migration tests start covering the six most recent migrations for the first time.

## 3. Build and install on the phone

1. Phone connected by USB, unlocked, USB debugging on.
2. The device dropdown in the top toolbar should show the phone rather than an emulator.
3. Press the green ▶ **Run** button, or `Shift+F10`.

This builds, installs and launches in one step.

**If it installs but behaves oddly after a database change**, Android is upgrading the
existing database. That is the intended path and how migrations get exercised — don't
uninstall to "clean up", because uninstalling deletes the data and hides migration bugs
rather than fixing them.

**Building a signed APK to keep** (rarely needed): main menu → `Build` →
`Generate Signed App Bundle / APK…` → `APK`.

---

## 4. Get a crash log

When the app dies on launch or mid-action, this is what turns "it crashed" into a fix in
one step rather than three guesses.

**The reliable version, in the Terminal:**

```
adb logcat -d -b crash
```

Copy everything from the line reading `FATAL EXCEPTION` down to the end and paste it into
the chat. The useful part is usually the first `Caused by:` line.

**GUI equivalent:** the `Logcat` tab along the bottom edge.

1. Choose the phone in the device dropdown at the top of that panel.
2. In the filter box, type: `package:com.carlmanning.carlsbrain level:error`
3. Reproduce the crash.
4. Select the red block that appears and copy it.

If `adb` is not recognised in the Terminal, use the Logcat tab instead — Android Studio
knows where `adb` lives even when the shell does not.

## 5. Run the migration test

Worth running after any database change, because it catches the exact class of bug that
crashed the app on launch in v2.8: a migration whose result does not match what Room
expects.

**This needs the phone connected** — it is an instrumented test and runs on the device.

- Open `carlsbrain/src/androidTest/java/com/carlmanning/carlsbrain/MigrationTest.kt`
- Click the green ▶ arrow in the left margin, next to the class name `MigrationTest`
- Choose **Run 'MigrationTest'**

The tests read the set of exported schemas at runtime and walk **every** one of them forward to
the newest, so coverage widens by itself as new schemas are committed — there is no version
number in the test file to keep updated. The last version had `LATEST_VERSION = 22` hardcoded
while the database was at 28, and passed anyway.

**Terminal equivalent:**

```
gradlew connectedAndroidTest
```

## 6. Run the fast tests (no phone needed)

These run on your machine in a couple of seconds and need no device.

**Android — Terminal:**

```
gradlew testDebugUnitTest
```

**Web app — Terminal, from the `webapp` folder:**

```
npm test
```

Worth running before a push. The web tests in particular cover the Drive file formats, which is
where every silent data-loss bug of the August review lived — a field dropped on a round trip,
invisible until a device restore.

## When git complains

**"Your local changes would be overwritten by merge"** — Android Studio has usually touched
a file under `.idea/` just by being open. Discard those and pull again:

```
git checkout -- .idea
git pull
```

**"Cannot find file to patch"** — an apply-patch attempt that should not have been used.
Use `git pull` instead; Claude pushes to the branch, so there is never a patch to apply.

**Push rejected** — the branch moved on GitHub since the last pull:

```
git pull
git push
```

**To see what state things are in**, this is always safe and changes nothing:

```
git status
git log --oneline -5
```

Paste the output into the chat if it looks wrong. It says more than a description does.

## The loop, in short

```
git pull          ← before anything else
▶ Run             ← build, install, launch
                  ← test it
adb logcat -d -b crash    ← only if it crashed
git add … && git commit && git push    ← only if you changed or generated something
```

The branch is `claude/jolly-mendel-c2w71n`. Everything Claude pushes goes there, and
`git pull` on that branch is all that is needed to receive it.
